# Cog-LoRA 基线复现方案

## 1. 目标与边界

目标是先证明历史代码、checkpoint、输入和环境能够重现论文基线，再进行可移植性修复和新实验。复现分两阶段：

1. **Phase A：兼容复现**。固定历史 commit，保留历史实现行为，得到可对照的输出；
2. **Phase B：受控迁移**。把必要代码迁入 `EEG_TMM`，一次只修一个问题，并对 Phase A 输出做回归测试。

位置角色：

- `EEG_DIFFUSION`：历史代码上游，只读；
- `CID_DATA_ROOT`：共享源数据和历史 checkpoint，只读；
- `EEG_TMM`：新代码、配置、manifest 和测试；
- `CID_ARTIFACT_ROOT`：所有新生成图、日志、指标和 checkpoint。

不在历史目录中写输出，不把整个 `EEG_DIFFUSION` 仓库复制或合并进 `EEG_TMM`，不覆盖任何已有实验目录。

## 3. Phase A：兼容复现

### A0. 准备独立 GPU 实例

使用有可见 NVIDIA GPU 的新实例和独立 clone。当前 CPU 实例不安装 PyTorch/CUDA，也不用于判断 checkpoint 是否可运行。

开始前记录：

- 实例名、GPU 型号和数量；
- 驱动、CUDA runtime、cuDNN；
- Python、PyTorch、torchvision；
- diffusers、transformers、PEFT、accelerate；
- pyiqa、LPIPS、xformers；
- SD-Turbo snapshot revision；
- 所有环境变量和完整 `pip freeze` 或 conda export。

若能找到原实验环境，优先导出版本；找不到时，在单独环境中按代码发布日期逐步重建。每次依赖组合都记录在新的运行目录，不原地升级一个已经产出结果的环境。

### A1. 确认 checkpoint 到实验条件的映射

由吴大伟确认至少三项：

1. 论文 Ours 的 checkpoint；
2. Static LoRA 的 checkpoint；
3. No guidance / frozen SD-Turbo 是否需要 checkpoint，以及准确入口。

选定后，对 checkpoint 计算 SHA-256，并把哈希、文件大小、模型类、训练配置、epoch、encoder 和 embedding 文件写入本次 run manifest。checkpoint 可复制到快速盘的只读 staging 目录，但源文件保持不变。

### A2. 冻结样本映射

不能继续依赖“数量一致 + 排序”作为正式配对依据。兼容复现时先导出历史顺序，但不改变它：

```text
sample_id
low_light_relative_path
ground_truth_relative_path
embedding_index
prompt_index
```

人工抽查首、中、末样本，并记录总数、重复 ID、缺失文件和图像尺寸。将小型 TSV/CSV 提交到 `splits/`，同时记录其 SHA-256。

### A3. 建立固定 smoke set

从正式 test split 选择至少 10 个固定 sample ID，覆盖不同类别和亮度。兼容运行必须固定：

- seed；
- prompt；
- precision；
- 输入尺寸和预处理；
- scheduler 配置；
- embedding 文件及索引；
- checkpoint SHA-256。

先只生成 smoke set，不直接运行完整测试集。

### A4. 原样运行历史实现

本阶段不得顺手修复以下行为：

- Cog-LoRA 中 U-Net timestep 为 `50`；
- 单步 scheduler 的 step 使用 scheduler 自身 timestep；
- Static LoRA/no-guidance 候选实现使用 `999`；
- 历史 prompt、precision 和预处理；
- 历史图像遍历顺序。

可以在外围 wrapper 中参数化输入输出位置和 GPU 可见性，但 wrapper 不改变张量、模型权重或计算路径。所有输出写入新目录：

```text
<CID_ARTIFACT_ROOT>/wudawei/baseline_compat/<timestamp>_<instance>_<git-sha>_seed<seed>/
```

最低保存内容：

```text
config.yaml
command.txt
git_commit.txt
legacy_commit.txt
checkpoint.sha256
sample_manifest.tsv
environment.txt
stdout.log
metrics.json
inference_images/
```

### A5. 兼容复现验收

依次通过以下 gate：

1. checkpoint 无 missing/unexpected key，或差异已明确记录；
2. 同一环境、同一 seed 重跑 smoke set，输出可重复；
3. smoke set 与留存的历史图片逐 sample 对齐，记录图像哈希及像素差；
4. 完整 test split 的样本数和 ID 全部匹配；
5. 使用历史评测路径得到与论文/历史记录足够接近的指标；
6. 重复结果异常涉及的目录经过输入、输出和图片哈希核查。

“足够接近”的数值容差必须在看新结果前写入配置，避免事后调整标准。

## 4. Phase B：受控迁移与修正

Phase A 通过后，从兼容运行创建新的任务分支。只迁移项目拥有且实际需要的文件；第三方库通过依赖管理安装，不复制 vendored 目录、模型权重或历史输出。

建议按以下顺序，每一步单独提交并与 Phase A smoke set 回归比较：

1. 把绝对路径改为 `CID_DATA_ROOT`、`CID_ARTIFACT_ROOT`、`CID_CACHE_ROOT` 或显式配置；
2. 去除模型内部 `.to("cuda")` 和入口 `cuda:3`，统一由调用端传入 device；
3. 用 sample-ID manifest 取代隐式排序配对；
4. 将生成和评测拆为独立命令，禁止复用或覆盖输出目录；
5. 固定并记录依赖、SD-Turbo revision、prompt、precision 和 scheduler；
6. 分别验证 timestep `50` 与 `999` 的语义和结果，再决定论文协议；
7. 建立统一 evaluator，并对每个指标补版本、输入范围和配对测试；
8. 建立 SD-Turbo、Static LoRA、Cog-LoRA 的统一 benchmark harness。

timestep 的改变会影响数值结果，必须作为显式实验变量，不作为普通重构混入。

## 5. 正式补实验放行条件

以下条件全部满足后，才开始多先验、效率、时间窗和 shuffle 的正式实验：

- 论文 Ours checkpoint 映射经作者确认；
- 固定 smoke set 兼容复现通过；
- 完整 test split 的 sample-ID 映射冻结；
- 环境与基础模型 revision 可重建；
- 统一 evaluator 在已知样本上验证；
- 每次运行自动写入唯一目录和完整元数据；
- Phase B 与 Phase A 的预期差异有回归记录。

当前直接阻塞项是：需要一台可见 NVIDIA GPU 的独立实例，以及论文最终 checkpoint/原工作环境版本的确认。等待这两项期间，可以继续做只读的 checkpoint 元数据审计和 sample-ID manifest 生成，但不应宣称已经复现基线。
